# ADR 0012: 재고 차감은 상품 행을 비관적 락으로 보호한다

Status: Accepted
Date: 2026-10-09

## Context

처음에는 조건부 UPDATE로 재고를 안전하게 차감할 수 있다고 판단했다. 이후 기존 `Stock.decrease()`를 어떻게 활용할지도 비교했다. 실험과 사고 흐름은 [설계 2.1](../week3/design.md#21-재고-차감)에 남긴다.

## Decision

상품을 ID 순으로 잠근 뒤 기존 `Stock.decrease()`와 JPA 변경 저장을 유지한다. 잠금 후 읽은 값으로 사전 검사하고 Stock도 자신의 규칙을 검사한다. 현재 상품 UPDATE가 재고 컬럼을 포함하므로 관리자 수정·삭제·재고 설정도 잠금 조회한다.

## Alternatives and costs

조건부 UPDATE의 정확성을 부정한 선택은 아니다. SQL·객체 상태를 따로 관리하는 비용보다 기존 행동을 유지하는 쪽을 택했다. SQL의 동시성 방어와 객체의 규칙 검사를 함께 두는 설계도 가능하며, 규칙 중복만으로 조건부 UPDATE를 배제한 것은 아니다. 성능 우위를 입증한 선택도 아니다. 낙관적 락은 충돌 후 처리를 추가로 정해야 한다. 비관적 락은 대기·교착 가능성을 남기므로 범위와 순서를 관리해야 한다.

검증 결과는 [구현 기록 2.1](../week3/implementation-log.md#21-재고-차감)에 둔다. Stock 소유 책임은 [ADR 0001](./0001-product-owns-stock.md)을 유지한다.

## 검증 방법과 확인 범위

[StockConcurrencyTest](../../apps/commerce-api/src/test/java/com/loopers/application/order/StockConcurrencyTest.java)는 실제 MySQL에서 데이터를 먼저 커밋하고, 별도 요청의 시작을 맞춘 뒤 모든 worker 종료 후 새 트랜잭션에서 결과를 읽는다.

| 검증 | 준비·실행 | 확인한 결과 |
|---|---|---|
| 잠금 없는 대조군 | 두 연결이 재고 5를 모두 읽도록 장벽을 두고 각각 상수 4를 저장 | 두 변경이 성공해도 최종 재고 4. UPDATE의 대기만으로 낡은 계산을 고치지 못함 |
| 초과 판매 방지 | 재고 5에 서로 다른 주문 8건이 각 1개 구매 | 성공 5건·거절 3건·기술 실패 없음·재고 0. 거절 주문은 DRAFT와 원래 잔액 유지 |
| 여러 품목의 잠금 순서 | 두 상품을 반대 순서로 담고 수량을 다르게 지정 | 둘 다 성공, 상품별 남은 수량 2, 결제액 3,000원. 품목별 수량이 섞이지 않음 |
| 다른 변경 경로 | 재고 설정·이름/가격 수정·브랜드 삭제를 주문과 각각 동시 실행 | 실행 순서에 맞는 결과만 허용하며 판매된 재고를 옛 값으로 덮어쓰지 않음 |
| 다른 상품에 대한 영향 | 한 상품의 잠금을 유지한 채 다른 상품 주문 실행 | 첫 잠금을 풀기 전에 다른 상품 주문 성공 |
| 실제 변경 뒤 실패 | 주문 저장 직전 flush하고 재고·잔액 SQL 반영을 조회한 뒤 예외 주입 | 재고 5·잔액 10,000원·DRAFT로 복구, 사용·추가 적립 기록도 복구 |

[StockTest](../../apps/commerce-api/src/test/java/com/loopers/domain/product/StockTest.java)는 차감과 부족·잘못된 수량 거절을 DB 없이 확인한다. 이 단위 테스트 자체가 동시성의 증거는 아니다.

반대 순서 주문의 통과는 해당 경쟁에서 교착이 발생하지 않았다는 증거이며, 모든 교착 가능성이 없어졌다는 보장은 아니다. 이 검증으로 조건부 UPDATE보다 빠르다고 판단하지 않는다.
