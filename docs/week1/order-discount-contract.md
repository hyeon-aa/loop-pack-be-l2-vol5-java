# 주문 쿠폰 할인 계약 설계

## 기준 문장

구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 한다.

---

## 0단계 — 기존 동작을 읽고 예상 상태를 적는다

### 기존 테스트(`ExampleV1ApiE2ETest`)의 세 경우

| 케이스 | 입력 | 확인된 상태 |
|---|---|---|
| 존재하는 ID | 저장된 exampleId | 2xx, data 필드(id/name/description) 일치 |
| 숫자가 아닌 ID | "나나" | 400 BAD_REQUEST |
| 존재하지 않는 ID | -1 | 404 NOT_FOUND |

> 실행 결과: `./gradlew :apps:commerce-api:test --tests '*ExampleV1ApiE2ETest'` → BUILD SUCCESSFUL, 3개 테스트 모두 통과.

### 네 입력 관찰 테스트(`ContractClassificationTest`)의 상태

| 가설 | HTTP Status | meta.result | errorCode | message | data 유무 |
|---|---|---|---|---|---|
| 존재하는 숫자 ID | 200 | SUCCESS | - | - | 있음 |
| abc | 400 | FAIL | Bad Request | 요청 파라미터 'exampleId' (타입: Long)의 값 'abc'이(가) 잘못되었습니다. | 없음 |
| 존재하지 않는 숫자 ID | 404 | FAIL | Not Found | [id = 999999] 예시를 찾을 수 없습니다. | 없음 |
| 미매핑 URL | 404 | FAIL | Not Found | 존재하지 않는 요청입니다. | 없음 |

> `ApiControllerAdvice`의 `handleNotFound(NoResourceFoundException)`과 `CoreException` 처리 경로를 보면, "존재하지 않는 ID"와 "미매핑 URL"은 원인은 다르지만 같은 404/NOT_FOUND 형태로 응답됨.
> 실행 결과: `ContractClassificationTest`에 4개 케이스 각각 HTTP status, meta.result, error code, data 유무를 assertion으로 작성 → `./gradlew :apps:commerce-api:test --tests 'com.loopers.interfaces.api.ContractClassificationTest'` → BUILD SUCCESSFUL, 4개 테스트 모두 통과.

## 1단계 — 기준 문장을 사실과 질문으로 나눈다

### 확인된 사실 (제품 약속) — 기준 문장에서 직접 확인됨

| ID | 확인된 사실 |
|---|---|
| PROMISE-001 | 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있다 |
| PROMISE-002 | 주문 확정 뒤 할인 금액은 바뀌지 않는다 |

### 실습 조건 — 이번 실습 범위로 주어진 조건

| ID | 실습 조건 |
|---|---|
| CONDITION-001 | 확정 전 한 주문에는 보유 쿠폰 한 장만 적용한다 |
| CONDITION-002 | finalAmount = originalAmount - discountAmount, 0 ≤ discountAmount ≤ originalAmount |
| CONDITION-003 | 같은 주문·쿠폰 재요청은 저장된 결과를 돌려주고 효과를 늘리지 않는다 |
| CONDITION-004 | 만료 여부는 요청 시작 시각으로 판단한다 |

### 제품 질문 (5개) — 모두 정책 확인 필요, 아래 설계 선택이 이 답을 대신하지 않음

| ID | 질문 | 답에 따라 달라지는 것 |
|---|---|---|
| QUESTION-001 | 주문 금액보다 쿠폰 금액이 더 큰 경우, 0으로 처리할지 적용을 막을지 | 사용자 응답 (할인 적용 성공 여부와 최종 결제 금액이 달라짐) |
| QUESTION-002 | 기존 쿠폰을 자동 취소하고 새 쿠폰을 적용하는지, 아니면 두 번째 쿠폰 적용을 거절하고 클라이언트가 명시적으로 교체 요청을 다시 보내게 하는지? | 사용자 응답 (기존 쿠폰이 자동 해제되는지, 새 쿠폰 적용 자체가 거부되는지) |
| QUESTION-003 | 미확정 주문의 할인 금액은 언제 고정되는가? (적용 시점 / 확정 시점 / TTL 후 재검증) | 저장 데이터 (스냅샷 시각·TTL 필드 필요 여부), 사용자 응답 (결제 시점에 금액이 바뀔 수 있는지, DECISION-002 참고) |
| QUESTION-004 | 운영자가 다른 사람의 쿠폰을 등록하거나, 다른 사람 주문에 쿠폰을 적용할 수 있나? (예: 이벤트 전 주문 고객 일괄 할인) | 권한 (운영자가 구매자와 동일한 제약을 받는지, 별도 권한을 갖는지) |
| QUESTION-005 | 원금(originalAmount)은 상품 가격의 합계인가, 아니면 상품 할인 등 다른 할인이 이미 반영된 금액인가? | 저장 데이터·사용자 응답 (할인 계산의 기준 금액이 달라지고, 그에 따라 실제 할인액의 상한과 최종 금액이 달라짐) |

## 2단계 — 여섯 규칙을 반례와 연결한다

| ID | 한줄정리 (상태 관계) | 출처 구분 |
|---|---|---|
| INV-001 | 요청의 X-USER-ID == 대상 주문의 buyerId (성공 처리된 모든 조회/변경 요청에서 성립) | 학습 본문 규칙 (기준 문장에 직접 명시는 없으나 "구매자는"에서 이어지는 소유권 규칙) |
| INV-002 | 주문 하나에 연결된 '적용됨' 상태의 쿠폰 레코드 수 ≤ 1 | 실습 조건 (CONDITION-001) |
| INV-003 | finalAmount = originalAmount - discountAmount, 0 ≤ discountAmount ≤ originalAmount | 실습 조건 (CONDITION-002) |
| INV-004 | 주문 확정 시점 t0에 기록된 discountAmount == 이후 임의 시점 t(t > t0)에 조회한 discountAmount | 제품 약속 (PROMISE-002) |
| INV-005 | 동일한 (orderId, couponId) 조합으로 [확정 전, 짧은 시간 내] 반복 요청 시 응답의 discountAmount는 최초 저장값과 같다 | 실습 조건 (CONDITION-003) |
| INV-006 | 쿠폰 유효 여부 = (서버가 요청을 수신한 시각 ≤ 쿠폰 만료 시각) | 실습 조건 (CONDITION-004) |

### INV-001 상세
- 규칙: 구매자는 자신이 소유한 주문만 조회/변경할 수 있다
- 깨지는 입력: A가 B의 주문번호를 조회한다면?
- 기대 결과: 본인 소유가 아니거나 존재하지 않는 주문이면 두 경우 모두 동일하게 `ORDER_NOT_FOUND`(404)로 처리한다. 다르게 응답하면 주문 존재 여부가 노출되므로 외부 응답을 같게 한다 (ERROR-001 설명 참고).
- 책임 후보: 주문 조회/변경 시 소유자(X-USER-ID) 검증 로직

### INV-002 상세
- 규칙: 확정 전 한 주문에는 보유 쿠폰 한 장만 적용한다
- 깨지는 입력: 보유쿠폰을 등록했다가 다른 쿠폰으로 변경하는 경우 / 쿠폰을 중복으로 등록하는 경우
- 기대 결과: 아직 안 정해짐 → QUESTION-002 참고 (자동 취소 후 재적용 vs 거절 후 명시적 교체 요청)
- 책임 후보: 주문별 쿠폰 정보 테이블 / 주문 테이블당 쿠폰 개수 제한 (중복 등록 시 쿠폰 데이터를 배열로 받을지, 단일 값만 허용할지 결정 필요)

### INV-003 상세
- 규칙: finalAmount = originalAmount - discountAmount이며 할인액은 0과 원금 사이다
- 깨지는 입력: 주문 금액이 10,000원인데 15,000원 할인 쿠폰을 적용하는 경우 (처리 방향은 담당자 확인 필요, QUESTION-001 참고)
- 기대 결과: 0으로 처리하는 방향을 고려 중이나, 구매자에게 불리할 수 있어 적용 자체를 막는 방향도 함께 검토 중 (미정, 담당자 확인 필요)
- 책임 후보: 주문정보 테이블 (원금·할인·최종금액 필드)

### INV-004 상세
- 규칙: 주문 확정 뒤 할인 금액은 바뀌지 않는다
- 깨지는 입력
  - 상황: 주문을 확정한 뒤, 관리자가 쿠폰 할인율을 10%에서 20%로 변경. 이후 그 주문의 내역을 다시 조회한다.
  - 문제: 시스템이 저장된 값 대신 매번 현재 정책으로 재계산하는 방식이면, 확정된 주문인데도 할인 금액이 정책 변경에 따라 달라져 보인다.
- 기대 결과: 주문 확정 시점의 할인 금액이 주문내역에 고정되어 있다.
- 책임 후보: 주문내역 테이블

### INV-005 상세
- 규칙: 같은 주문·쿠폰 재요청은 저장된 결과를 돌려주고 효과를 늘리지 않는다
- 검토했지만 반례 아님
  - 상황: A 상품 주문 생성 후 쿠폰 적용. 결제하지 않고 이탈해 주문이 취소됨. 이후 다시 주문하니 그 사이 A 가격이 인상된 상태.
  - 판단: 다시 만든 주문은 orderId가 다른 별개의 요청이므로, 이 규칙(같은 orderId·couponId 재요청)이 다루는 케이스가 아님.
- 깨지는 입력(진짜 반례)
  - 상황: A 상품 주문 생성 후 쿠폰 적용. 화면을 그대로 둔 채 10분 경과. 그 사이 A 가격이 인상됨. 이 상태에서 결제 확정.
  - 판단: orderId·couponId는 동일하지만, snapshot과 재계산 중 어떤 결론을 내리는지에 따라 결과가 달라짐 (DECISION-002 참고).
- 기대 결과: 이 경우 저장된 결과를 그대로 반환하면 안 되며, 같은 주문과 쿠폰 재요청이라도 실제 결제 시점의 금액으로 반영되어야 한다.
- 책임 후보: 주문정보 테이블 (스냅샷 값 저장 위치)

### INV-006 상세
- 규칙: 만료 여부는 요청 시작 시각으로 판단한다
- 깨지는 입력: 쿠폰 만료일이 자정까지인데, 23시 59분에 요청이 들어오고 실제 처리는 다음날 00시 01분에 완료되는 경우
- 기대 결과: 요청 시작 시간 기준이므로 쿠폰 적용된다.
- 책임 후보: 주문정보 테이블 (요청 수신 시각 저장 위치, 완료 여부는 별도 필드로 이후 갱신)

### 참고 — 이번 주 범위 밖 (발견만 해둠)
- 쿠폰도 주문처럼 소유자 검증이 필요할 수 있다 (INV-001과 같은 패턴). 남의 쿠폰 ID로 적용을 시도하는 경우를 어떻게 처리할지는 이번 주 필수 범위(INV-001~006)에 포함하지 않는다.
- 이 "쿠폰 소유권 위반"은 "만료/이미 사용"(ERROR-003)과는 성격이 다른 별개 오류 카테고리다.

## 3단계 — 외부 계약과 내부 경계를 선택한다

### API 모양

| 항목 | 내용 |
|---|---|
| Method/Path | `POST /api/v1/orders/{orderId}/discount` |
| Request | couponId |
| Response | originalAmount / discountAmount / finalAmount |

### 오류 리스트

| ID | 케이스 | 도메인 코드 | HTTP | 판단 근거 | 사용자 다음 행동 |
|---|---|---|---|---|---|
| ERROR-001 | 존재하지 않는 주문 조회 / 다른 사람 주문 조회 | `ORDER_NOT_FOUND` | 404 | 두 경우를 외부에서 구분하지 않음 (아래 설명) | 내 주문 id로 조회 |
| ERROR-002 | 이미 확정된 주문에 쿠폰 적용 시도 | `ORDER_ALREADY_CONFIRMED` | 409 | 기준 문장상 확정 전에만 적용 가능, 확정된 주문은 상태상 불가 (DECISION-003의 순서 2 검증 실패) | 할인 없이 진행하거나 문의 |
| ERROR-003 | 적용 불가한 쿠폰 (만료/이미사용) | `COUPON_STATE_INVALID` | 422 | 쿠폰 상태(유효성) 문제. 만료·이미사용은 다음 행동이 같아 하나로 묶고 message로만 구분 | 다른 쿠폰 선택 |
| ERROR-004 | 요청 값 형식 오류 (orderId 타입, couponId 누락 등) | `INVALID_REQUEST` | 400 | 요청 본문을 해석하거나 검증할 수 없음 | 요청 본문 수정 |
| ERROR-005 | 더블클릭 — 처리 중 동시 요청 (첫 요청이 아직 처리 중일 때 같은 요청이 또 옴) | `REQUEST_IN_PROGRESS` | 409 | INV-005가 다루지 않는 진짜 동시성 문제, 아직 결과 없음 | 잠시 후 재시도 (또는 락으로 대기 후 첫 요청 결과 반환) |

더블클릭이라도 첫 요청이 이미 완료돼 결과가 저장된 뒤의 재요청은 오류가 아니라 기존 성공 결과를 반환하는 정상 흐름이므로 이 표에 넣지 않는다 (INV-005).

ERROR-001 (존재하지 않는 주문 / 다른 사람 주문): 내부에서는 '주문 없음'과 '권한 없음'을 구분해 판단하되, 외부 응답은 도메인 코드·HTTP status·message·body를 완전히 동일하게 한다. 두 경우를 다르게 응답하면(예: 권한 없음을 403으로) 공격자가 주문 ID를 여러 개 넣어보며 "이 ID는 실제로 존재한다(403)" vs "존재하지 않는다(404)"를 구분할 수 있다. 그래서 주문 존재 여부 자체를 숨긴다.

ERROR-003 (적용 불가한 쿠폰 - 만료/이미사용): 정상적으로 서비스를 이용하는 과정에서 자연스럽게 발생하는 상황이다 (쿠폰함 조회 시점에는 유효했으나 이후 만료되거나 이미 사용된 경우). "쿠폰 상태(유효성)" 문제이므로 다음 행동이 항상 "다른 쿠폰 선택"으로 동일 → 메시지만 다르게 하고 코드는 하나로 통일한다.

### DECISION-001 — 오류를 구분하는 방식

| 결정 항목 | 선택 | 버린 대안 | 이유 |
|---|---|---|---|
| 표현 방식 | HTTP reason phrase 대신 실패 원인을 가리키는 도메인 코드(`ORDER_NOT_FOUND` 등)를 두고, HTTP status는 API 계층에서 변환한다 | 기존 ErrorType의 HTTP reason phrase 코드(`Not Found` 등) 그대로 사용 | `Not Found`만으로는 '주문 없음'인지 '쿠폰 없음'인지 클라이언트가 구분 못 한다. 안정된 의미 코드가 있어야 클라이언트가 errorCode로 분기할 수 있다. |
| 묶는 범위 | 클라이언트의 다음 행동이 같은 원인은 코드 하나로 묶고 message로만 구분 (만료·이미사용 → `COUPON_STATE_INVALID`, 남의 주문·없는 주문 → `ORDER_NOT_FOUND`) | 원인마다 코드를 전부 분리 (`COUPON_EXPIRED`, `COUPON_ALREADY_USED` 등) | 만료된 쿠폰과 이미 사용한 쿠폰은 원인은 다르지만 프론트가 하는 일은 똑같다(둘 다 "다른 쿠폰 선택"). 프론트가 똑같이 처리한다면 코드를 나눠도 쓸 데가 없고, 이런 식으로 원인마다 코드를 만들면 관리할 코드만 계속 늘어난다. 그래서 지금은 하나로 묶는다. 나중에 "만료일 때만 다른 화면을 보여줘야 한다" 같은 요구가 생기면 그때 `COUPON_EXPIRED` 등으로 나눈다. 지금도 내부에서는 만료/이미사용을 구분해 판단하므로, 그때는 외부 코드만 추가하면 된다. |

### DECISION-002 — snapshot과 재계산

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 쿠폰 적용(POST /discount) 시점에 값 고정, 이후 가격 변동 무시 | 사용자가 본 값 그대로 보장 | 서비스가 가격 변동 리스크를 무기한 떠안음 (INV-005 문구를 문자 그대로 읽으면 이 옵션) |
| B | 확정(confirm) 시점에 실제로 계산해서 고정 (적용 API는 미리보기일 뿐) | INV-005 10분 뒤 가격변동 반례가 자연 해결 | 사용자가 본 금액과 결제 금액이 달라질 수 있음 → 금액 불일치에 대한 클레임 소지 |
| C | 적용 시점 스냅샷 + 짧은 TTL(10~15분), 만료 시 재계산 + 안내 | A/B 절충 | TTL 값, 만료 시 UX를 추가로 정해야 함 |

C안에서 더 고민되는 지점: TTL 안에서 가격이 바뀌면 그냥 이전 값으로 계산해주는 건지?
- 시간 기준: TTL 안이면 가격이 바뀌었든 말든 옛날 값 유지
- 이벤트 기준: 확정 시점에 실제로 가격이 스냅샷 때와 같은지 비교해서, 바뀌었으면 TTL 안 지났어도 무효화

| 선택 | 버린 대안 | 이유 |
|---|---|---|
| 쿠폰 적용 시점에 값을 스냅샷으로 저장하고, 짧은 유효시간(TTL) 동안 유지. 확정 직전에 한 번 더 유효성 재검증해 가격/쿠폰 변동 반영 | 무기한 스냅샷 유지 (A) / 매번 실시간 재계산 (B) | 확정된 주문의 금액 불변(INV-004)은 지켜야 하지만, 미확정 상태에서 무기한 옛날 가격을 보장하는 것도 리스크가 크다 |

### DECISION-003 — 호출 순서를 숨길 책임 경계

쿠폰 적용 API(`POST /discount`) 안에서 순서대로 필요한 검증/계산 단계:

| 순서 | 단계 | 관련 규칙 |
|---|---|---|
| 1 | 주문이 존재하고 내 것인가? | INV-001 |
| 2 | 주문이 아직 확정 전인가? | - |
| 3 | 쿠폰이 만료/이미사용 안 됐는가? | INV-006, ERROR-003 |
| 4 | 이미 다른 쿠폰이 적용돼 있진 않은가? | INV-002 |
| 5 | 할인 금액 계산 | INV-003 |
| 6 | 계산 결과를 스냅샷으로 임시 고정 (확정 전까지 이 값 유지, TTL 적용) | INV-004, INV-005, DECISION-002 |
| 7 | 최종 금액 응답 | - |

별도 흐름(주문 확정 API): 위 1~7과는 다른 API 호출 시점에 일어나는 단계.

이유: 1~7은 쿠폰 적용 API(`POST /discount`) 한 번의 호출 안에서 스냅샷을 만들고 저장하는 단계다. 반면 8번은 사용자가 결제를 확정하는 별도 시점(별도 API 호출)에 일어나며, 7번과 8번 사이에는 TTL만큼의 시간 간격이 벌어질 수 있다. 스냅샷을 "만드는" 책임(1~7)과 그 스냅샷을 "검증하고 최종 반영하는" 책임(8)이 서로 다른 호출·시점에 속하므로 같은 흐름으로 묶지 않았다. 또한 이번 주 기본 장면은 `POST /discount`만 다루므로, 확정 API의 상세 설계는 범위 밖이다.

| 순서 | 단계 | 관련 규칙 |
|---|---|---|
| 8 | 주문 확정 시점에 스냅샷 값과 현재 가격/쿠폰 상태를 비교해 유효성 재검증 | DECISION-002 |

> 8번은 1~7과 같은 Facade가 맡을지, 확정을 담당하는 별도 컴포넌트가 맡을지는 이번 주 범위에서 정하지 않음.

| 선택 | 버린 대안 | 이유 |
|---|---|---|
| Order 엔티티가 아니라 별도의 Facade/Service(예: OrderDiscountFacade)가 위 7단계 전체를 책임진다. Controller는 이 Facade의 메서드 하나만 호출하고 내부 순서는 모른다. | Order 엔티티 안에 이 검증/계산 로직을 전부 메서드로 넣는 방식 | 검증 단계가 7개나 되는데, 이걸 Order 엔티티에 다 넣으면 Order가 "주문 데이터 표현"과 "외부 조건 검증·조율"을 동시에 떠맡아 너무 무거워진다. 검증·조율은 별도 계층으로 분리해 Order를 가볍게 유지하는 편이 낫다. |

## 도구(Claude)가 제안한 내용 — 채택/보류/거절

> 도구가 제안한 내용은 제품 정책으로 바로 채택하지 않는다. 출처가 없으면 보류 또는 거절로 표시하고 이유를 적는다. 제안이 없었다면 해당 없음이라고 쓴다.

| 제안 | 판단 | 비고 |
|---|---|---|
| 더블클릭 시 처리 | 채택 | 완료 후 재요청(정상 흐름, INV-005)과 처리 중 동시 요청(ERROR-005)으로 구분함 |
| 쿠폰 수량 제한 시 동시성 ("선착순 100장") | 보류 | 요구사항에 명시된 범위(단일 쿠폰·단일 주문 흐름)에 포함되지 않아 이번 범위에서 제외 |
| 확정 후 주문 취소/환불 시 쿠폰 처리 | 보류 | 요구사항에 명시된 범위(적용 흐름)에 포함되지 않아 이번 범위에서 제외 |
