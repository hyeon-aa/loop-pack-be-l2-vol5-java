## 조회 계약과 측정 환경

상품 10,000건에서 SQL 원리를 확인하고, 100,000건을 복사한 실험 DB에서 실제 앱을 비교한다. 원본 DB·개발 DB와 분리한 benchmark MySQL 8.0.46·InnoDB·REPEATABLE READ를 사용한다. 기존 상품 인덱스와 상품별 좋아요 카운터를 유지한다. 설정은 [setup.md](setup.md)를 따른다.

가격순은 `price ASC, createdAt DESC, id DESC`다. 브랜드 필터·삭제 상품/브랜드 제외·상품 표시 필드·현재 좋아요 수·page/size 검증을 지킨다. 좋아요순은 전체 후보의 좋아요 수로 정렬한 뒤 페이지를 선택한다. 빈 페이지는 빈 items로 반환하고 totalCount·hasNext는 제공하지 않는다.

총상품수 제외 결정의 이유와 응답 영향은 [ADR 0022](../adr/0022-product-list-without-total-count.md#이유와-결정)를 따른다.

## 실험을 읽는 방법

EXPLAIN으로 선택한 인덱스·예상 행 수·추가 정렬을 보고, EXPLAIN ANALYZE로 실제 단계별 반환 행·시간을 확인한다. 같은 연결에서 일반 SELECT 직전·직후 Handler 카운터 차이를 측정해 내부 읽기 요청을 보조 확인한다. Handler는 정렬의 CPU 작업, 디스크 읽기나 Root·Branch·Leaf 방문 횟수를 직접 보여주지 않는다.

결과 필드·순서를 먼저 확인하고, 읽는 범위·정렬·실제 행 조회와 시간을 함께 판단한다. 적게 읽었다는 사실만으로 API 전체가 빨라졌다고 결론 내리지 않는다. 직접 관찰한 결과와 구조에 대한 설명은 구분한다. 완료한 검증은 [implementation-log.md](implementation-log.md)에 기록한다.

### Handler 측정 도구의 자동 조회

현재 MySQL 확장은 일반 상품 SELECT 뒤 결과 전체 건수를 표시하려고 LIMIT 없는 COUNT를 자동으로 보냈다. 상품 페이지 20개 읽기 외에 COUNT의 99개 읽기가 합쳐질 수 있다. 실제 SQL 로그로 이를 확인했다. Handler로 페이지 SELECT만 평가할 때는 실행기의 같은 연결에서 구간을 통제한다. 현재 상품 목록 API에는 총상품수 COUNT가 없다. 확장의 표시용 자동 COUNT와 실제 API의 SQL을 구분한다.

## 상품 인덱스 실험

각 절의 인덱스 추가·삭제·유지는 해당 실험 시점의 기록이다. 현재 인덱스별 용도와 남은 판단은 [현재 조회 흐름과 인덱스](#current-query-flow)에서 함께 확인한다.

### 준비: 브랜드 7 조건으로 범위를 좁힌 조회

처음에는 전체 활성 상품을 가져와 Java에서 브랜드 7을 골랐다. 브랜드 조건을 SQL에 전달하면서 기존 `(brand_id, deleted_at)` 인덱스로 해당 구간을 찾게 됐다. 이 준비 단계에서는 정렬·LIMIT을 넣지 않았다.

```sql
SELECT p.*
FROM product p
WHERE p.brand_id = 7 AND p.deleted_at IS NULL;
```

전체 조회는 상품 10,000개를 훑고 9,699개를 반환했다. 브랜드 조건 조회는 99개를 읽고 반환했다. 인덱스를 새로 추가한 효과가 아니라 기존 인덱스로 필요한 범위를 찾도록 조건을 DB에 전달한 효과다. [실행 SQL](../../scripts/sql/week4-01-brand-filter.sql).

구조를 설명하면 Root·Branch를 거쳐 브랜드 7·미삭제 구간을 찾고 Leaf 항목을 따라 읽는다. SELECT p.\*에는 이름·가격처럼 기존 보조 인덱스에 없는 컬럼이 있으므로 기본키로 상품 행도 가져와야 한다. 이 그림은 구조 설명이며 실제 페이지 방문을 측정한 것은 아니다.

### 1. 가격순 정렬만 추가

상품 99개를 가격순으로 반환하기 위해 ORDER BY만 추가했다. 같은 가격의 순서도 일정하게 유지하려고 생성 시각·ID 내림차순을 포함한다.

```sql
SELECT p.*
FROM product p
WHERE p.brand_id = 7 AND p.deleted_at IS NULL
ORDER BY p.price ASC, p.created_at DESC, p.id DESC;
```

기존 브랜드 인덱스에는 가격 순서가 없으므로 해당 상품 99개를 읽은 뒤 별도로 정렬한다. SQL 반환도 99개다. **이 변경은 결과 순서를 맞추며 읽는 상품 수를 줄이지 않는다.** LIMIT·새 인덱스·좋아요는 이번 단계에 추가하지 않았다. [실행 SQL](../../scripts/sql/week4-02-price-sort.sql).

현재 읽기 흐름은 다음과 같다.

```text
브랜드 인덱스의 해당 구간 찾기
→ 상품 99개 읽기
→ 가격·생성 시각·ID 순서로 정렬
→ 상품 99개 반환
```

### 2. 가격순 20개 쿼리를 고정한 기존 인덱스 기준선

같은 쿼리를 고정하고 인덱스에 따른 탐색을 비교한다. 앞의 SQL 변경 단계는 준비 과정이다. 상품의 삭제 조건·동점 정렬을 유지하고 필요한 컬럼을 명시했다. 조회 컬럼을 바꾼 비교와 인덱스를 바꾼 비교는 구분한다.

```sql
SELECT id, brand_id, name, price, created_at
FROM product
WHERE brand_id = 7 AND deleted_at IS NULL
ORDER BY price ASC, created_at DESC, id DESC
LIMIT 20;
```

기존 `(brand_id, deleted_at)` 보조 인덱스의 같은 값 구간에서는 기본키 ID가 순서를 정한다. ID 순서로 조회한 예시는 `(id, price)`가 `(7, 26000) → (107, 96000) → (207, 66000) → (307, 36000) → (407, 6000)`이었다. 가격순이 아니므로 처음 발견한 20개를 바로 반환할 수 없다.

```text
기존 브랜드 인덱스에서 (7, NULL) 구간 시작점 찾기
→ 해당 구간 항목을 따라 읽기
→ 기본키로 이름·가격·생성 시각을 가져오기
→ 후보 99개에서 가격순 상위 20개 선택
→ 20개 반환
```

직접 확인한 계획은 Index lookup 99행 → Sort → Limit 20행이었다. Using index condition은 커버링을 뜻하지 않는다. 이름·가격·생성 시각은 기존 인덱스에 없으므로 일반적인 보조 인덱스 접근에서 실제 행 조회가 필요하다. Handler는 이 InnoDB 내부 기본키 조회를 별도 횟수로 보여주지 않는다. 트리 높이와 실제 페이지 방문은 이번에 측정하지 않았다.

[실행 SQL](../../scripts/sql/week4-03-fixed-product-page.sql)에 인덱스 키 순서를 이해하는 보조 조회도 넣었다. 보조 조회에만 FORCE INDEX와 ORDER BY id를 사용하며 고정 측정 SQL에는 힌트가 없다. 물리 Leaf 페이지를 덤프한 것은 아니다. 새 인덱스는 아직 추가하지 않았으며, 다음에는 동일 쿼리에서 인덱스 후보를 검토한다.

### 3. 가격 정렬용 복합 인덱스

같은 기준 쿼리를 유지하고 `(brand_id, deleted_at, price ASC, created_at DESC, id DESC)` 인덱스를 추가했다. WHERE의 앞 두 값이 고정된 구간 안에서는 ORDER BY의 세 컬럼 순서가 맞는다. 가격을 WHERE로 지정하지 않아도 해당 구간 시작점부터 가격순으로 읽을 수 있다. 결과 순서는 SQL의 ORDER BY가 보장한다.

#### 쿼리 패턴과 인덱스 컬럼의 대응

선정의 출발점은 **브랜드 조건이 있는 가격순 첫 20개 조회**다. 실제 서비스에서 가장 자주 호출되는 쿼리라고 측정한 것은 아니며, 이번 주차에 최적화 대상으로 정한 조회 패턴에 맞춰 설계하고 검증했다. WHERE·ORDER BY·LIMIT을 함께 보고 다음 역할을 컬럼 순서에 반영했다.

| 쿼리 패턴 | 인덱스에 반영한 이유 |
| --- | --- |
| `brand_id = ?` | 해당 브랜드 구간부터 찾는다. |
| `deleted_at IS NULL` | 같은 브랜드 안에서 미삭제 상품 구간으로 좁힌다. |
| `ORDER BY price ASC` | 앞 두 값이 고정된 구간을 가격 오름차순으로 읽는다. |
| `created_at DESC, id DESC` | 같은 가격에서도 API가 요구하는 생성 시각·ID의 동점 순서를 맞춘다. |
| `LIMIT 20` | 앞의 조건과 정렬을 인덱스로 처리해 첫 20개를 채우면 멈춘다. |

실제 API는 활성 브랜드 검사도 수행한다. 위 표는 상품 인덱스에 대응하는 조건·정렬을 설명하며, API의 모든 SQL을 이 인덱스 하나로 처리한다는 뜻은 아니다. [실제 조회 쿼리](../../apps/commerce-api/src/main/java/com/loopers/infrastructure/product/ProductJpaRepository.java).

카디널리티는 서로 다른 값의 수이며 컬럼 순서를 결정하는 단독 기준으로 삼지 않는다. 예를 들어 미삭제 상품이 많아 `deleted_at IS NULL`만으로 줄일 수 있는 행이 적더라도, 이번 쿼리에서는 브랜드와 삭제 상태를 고정한 뒤 가격순으로 읽는 역할이 있다. 고유값이 많은 컬럼을 무조건 앞에 두기보다 쿼리의 조건·정렬과 실제 읽기량을 함께 본다.

다만 이 쿼리에서는 `brand_id`와 `deleted_at`이 모두 고정되므로, 이 실험만으로 두 컬럼의 선후관계가 유일한 최적이라고 증명하지는 않았다. 브랜드를 선두에 둔 구성은 브랜드별 상품 조회·삭제 대상 조회 등 다른 패턴과도 맞으며, 기존 브랜드 인덱스와의 대체 가능성은 6절에서 별도로 비교했다. 모든 컬럼 순열을 비교한 것은 아니다.

이 사례는 **값을 고정하는 조건을 앞에 두고 그 구간 안의 정렬을 뒤에 맞춘 선택**이다. 모든 WHERE 컬럼을 정렬 컬럼보다 앞에 두는 공식으로 일반화하지 않는다. 범위 조건이나 여러 값을 합치는 IN 조건이 끼면 뒤 컬럼의 탐색·정렬 활용이 달라질 수 있으며, IN의 실제 결과는 8절에 기록했다. [MySQL 복합 인덱스](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html), [ORDER BY 최적화](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html).

```text
가격 인덱스의 (7, NULL) 구간 시작점 찾기
→ 가격 ASC·생성 시각 DESC·ID DESC 순서로 항목 읽기
→ 항목의 ID로 실제 행에서 이름 가져오기
→ 20개를 채우면 종료
```

기존 인덱스의 99행 접근과 Sort가 새 인덱스에서 20행 접근·Sort 없음으로 바뀌었다. Handler는 key 1·next 99에서 key 1·next 19로 바뀌었다. 첫 항목과 이후 19개를 얻는 읽기 흐름과 맞는 결과다. 이름은 인덱스에 없으므로 아직 커버링 조회가 아니다.

기존 브랜드 인덱스는 비교를 위해 유지했다. 선두 열 중복에 따른 저장·쓰기 비용은 정리 여부를 판단할 때 검토한다. 상품 가격·생성 시각·이름 등의 쓰기 비용은 이번 단계에서 측정하지 않았다. 이번 결과는 브랜드 조건이 있는 고정 SQL의 탐색이며 전체 API·브랜드 없는 조회의 개선을 보장하지 않는다. [실행 SQL](../../scripts/sql/week4-05-price-index.sql).

#### 가격까지만 포함한 후보와 전체 정렬 비교

ORDER BY의 모든 열을 인덱스에 반드시 넣어야 하는 것은 아니다. 인덱스는 별도 정렬 없이 같은 순서를 만들려는 선택이다. 같은 쿼리에서 `(brand_id, deleted_at, price)` 후보도 비교했다. 가격까지만 있는 후보는 같은 가격 안에서 생성 시각 DESC·ID DESC가 맞지 않아 이번 계획에서 99개를 읽고 Sort를 수행했다. 전체 정렬 후보는 20개만 읽고 Sort가 없었다. 두 후보의 결과는 같았다.

짧은 인덱스는 약 320KiB, 전체 정렬 인덱스는 약 400KiB로 관찰됐다. 이는 InnoDB 인덱스 페이지 할당 통계이며 정확한 유효 데이터 크기는 아니다. 동점 정렬을 포함하면 인덱스가 커지는 비용 대신 이번 쿼리의 읽기·정렬을 줄였다. 쓰기 시간은 별도 측정하지 않았다. 전체 정렬 인덱스를 유지하고 짧은 후보는 실험 후 삭제했다. 조건·데이터·정렬이 바뀌면 다시 판단한다.

#### 가격까지만 있는 후보의 자동 선택 재검토 기록

사용자가 전체 정렬 인덱스를 삭제하고 `(brand_id, deleted_at, price)` 후보만 추가한 상태에서 다시 확인했다. 힌트 없는 SQL은 기존 브랜드 인덱스를 선택했다. 가격 후보를 FORCE INDEX로 사용해도 같은 99개를 읽고 Sort를 수행했다. 두 경로 모두 WHERE의 같은 99개를 찾고, 같은 가격 안의 생성 시각·ID 내림차순을 별도로 해결해야 했다.

optimizer trace에서는 두 ref 후보의 예상 rows가 99, cost가 34.65로 같았고 기존 인덱스가 선택됐다. 범위 후보 평가도 두 cost가 34.91로 같았으며 가격 후보는 chosen=false·cause=cost였다. 표시된 정밀도로는 새 후보의 비용 우위가 없었다는 것까지 확인하며, 동률에서 기존 인덱스를 고른 정확한 내부 tie-break까지 증명했다고 보지 않는다.

현재 고정 쿼리에서는 가격까지만 있는 후보가 읽기·정렬을 줄이지 않아 별도 유지할 근거가 약하다. 하지만 가격만 정렬하거나 가격 범위를 거르는 다른 쿼리에서는 도움이 될 수 있다. 모든 쿼리에서 불필요한 인덱스라고 일반화하지 않는다. 사용자 직접 실험 중인 짧은 후보는 이번 확인에서 삭제하지 않았다.

옵티마이저는 후보를 모두 실행해 시간을 비교하는 것이 아니라 실행 전에 통계·인덱스 구조·조건·정렬·필요 컬럼을 바탕으로 비용을 추정한다. cost는 실제 밀리초가 아니다. 새 인덱스가 생겼다고 자동으로 채택하지 않으며, 기존 인덱스가 항상 우선한다는 규칙으로 해석하지 않는다. 예상의 정확성은 ANALYZE·Handler·실제 시간으로 확인한다.

### 4. 기본키 자동 포함과 정렬 방향은 다르다

05 인덱스에서 id DESC만 뺀 `(brand_id, deleted_at, price ASC, created_at DESC)` 후보를 비교했다. InnoDB 보조 인덱스는 기본키 ID를 자동 포함하므로 상품 행을 찾거나 ID 값을 얻는 데는 별도 id 선언이 필요하지 않다. 하지만 자동 포함 기본키 순서와 쿼리의 id DESC 요구는 구분한다.

같은 가격·생성 시각의 보조 조회에서 ID 1407 → 4407 → 7407이 나타났고, 그 ASC 순서 쿼리는 Using index·filesort 없음이었다. 원래 쿼리는 7407 → 4407 → 1407의 DESC 순서를 요구한다. 후보는 99개를 읽고 Sort로 원래 결과를 만들었고 05는 20개를 읽고 Sort 없이 같은 결과를 만들었다.

id DESC는 정확한 결과를 얻기 위해 반드시 넣는 열이 아니라, 이번 ORDER BY 전체를 인덱스로 처리하려고 방향을 명시한 것이다. 가격 ASC·생성 시각 DESC를 유지하면서 ID만 반대로 정렬하는 요구이므로 전체 인덱스를 역방향으로 읽는 것만으로 해결하지 않는다. 크기는 두 후보 모두 통계상 400KiB였으며, 기본키가 자동 포함되기 때문에 id를 명시했다고 별도 ID가 중복 추가됐다고 해석하지 않는다. [확인 SQL](../../scripts/sql/week4-06-implicit-id.sql). 비교용 후보는 삭제하고 05를 유지했다.

### 5. 커버링: 이름 제외와 이름 인덱스 추가

05 인덱스에는 브랜드·삭제 상태·가격·생성 시각·ID가 있지만 이름은 없다. 이름을 포함한 조회는 실제 상품 행에서 이름을 가져와야 한다. SELECT에서 이름만 제외한 원리 실험에서는 Using index·Covering index lookup이 나타났다. 두 조회 모두 상품 20개·Sort 없음·Handler key 1·next 19였다. 내부 기본키 조회는 Handler에 별도로 표시되지 않으므로 카운터가 같아도 커버링 여부는 다르다.

실제 API에는 이름이 필요하므로 이름 제거를 적용안으로 삼지 않는다. 사용자 제안으로 `(brand_id, deleted_at, price ASC, created_at DESC, id DESC, name)`도 비교했다. 정렬 기준 뒤에 이름을 넣어 원래 순서를 유지했고 이름을 포함한 원래 쿼리도 커버링 계획으로 바뀌었다. 같은 20개와 모든 필드를 반환했다.

이름 후보의 인덱스 할당량은 약 1,552KiB로 05의 400KiB보다 컸다. 이름 변경과 등록·삭제 때 추가 유지 비용도 고려해야 한다. 서버 SQL 중앙값 차이는 작았고 상품 20개만 가져오는 상황에서 실제 API·쓰기까지의 이득은 아직 확인하지 않았다. 이름 후보는 비교 후 삭제하고 05를 유지한다. 커버링이라는 이유만으로 즉시 채택하지 않는다. [확인 SQL](../../scripts/sql/week4-07-covering.sql).

Covering 계획은 필요한 값이 인덱스에 있어 일반적인 컬럼 확보 목적의 재조회를 줄인다는 근거다. MVCC 가시성 확인 등 모든 내부 상황에서 기본키 접근이 반드시 0임을 물리적으로 측정한 결과는 아니다.

#### 기억할 커버링의 의미

커버링은 인덱스 안에서 찾는 과정 자체를 없애는 것이 아니다. 쿼리에 필요한 값이 보조 인덱스에 모두 있어서 다른 컬럼을 얻기 위해 기본키로 실제 행을 다시 찾는 과정을 줄이는 것이다. SELECT뿐 아니라 WHERE·ORDER BY에 필요한 컬럼도 함께 본다. 같은 인덱스도 이름을 포함하는 쿼리와 제외하는 쿼리에서 커버링 여부가 다를 수 있다.

### 6. 기존 브랜드 인덱스의 선두 컬럼 대체 검토

#### 비교 전 확인할 점: 선두 컬럼 중복

idx_product_brand_price의 앞 두 컬럼은 idx_product_brand_deleted와 같은 `(brand_id, deleted_at)`이다. 복합 인덱스의 왼쪽 연속 컬럼으로도 탐색할 수 있으므로 브랜드·삭제 조건만으로 조회하는 경우 긴 인덱스의 앞부분을 사용할 수 있다. 물리적으로 인덱스를 잘라 별도 생성하는 것은 아니다. [MySQL 복합 인덱스 문서](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html).

다만 같은 조건을 찾을 수 있다는 사실만으로 모든 경로에서 짧은 인덱스가 불필요하다고 확정하지 않는다. 짧은 인덱스가 더 작을 수 있고, `(brand_id, deleted_at)`의 같은 값 안에서는 자동 포함 기본키 ID 순서인 반면 긴 인덱스는 가격·생성 시각·ID 순서다. 브랜드 일괄 삭제의 활성 상품 ID 조회는 ORDER BY id이므로 긴 인덱스로 대체할 때 Sort가 생기는지도 확인해야 한다. 잠금은 이후 단건 PK 순서로 얻는 기존 경계를 유지한다.

삭제 여부는 브랜드 조건 조회·COUNT·브랜드 삭제 대상 ID 조회 등 실제 SQL을 긴 인덱스로 처리했을 때의 결과·읽기·정렬과 인덱스 유지 비용을 비교한 뒤 결정한다. 기존 인덱스는 삭제하지 않았다. 아래 읽기 경로 대체 비교는 완료했으며 쓰기·삭제 전체 성능 검증은 남아 있다.

#### 비교 결과와 유지 판단

기존 인덱스를 삭제하지 않고 실제 세 조회 형태를 각각 기존·긴 인덱스로 강제해 비교했다. 브랜드 상품 조회와 활성 상품 COUNT는 긴 인덱스의 앞 두 컬럼으로 같은 범위를 찾았다. 두 경로 모두 99개를 읽고 같은 결과를 반환했다.

브랜드 삭제 대상의 `SELECT id ... ORDER BY id`는 달랐다. 기존 인덱스의 같은 브랜드·삭제 상태 구간은 ID 순서라 추가 정렬이 없고, 긴 인덱스는 가격·생성 시각·ID 순서라 별도 Sort가 추가됐다. 같은 조건을 탐색하는 기능은 겹치지만 모든 정렬을 동일하게 처리하지는 않는다.

이번에는 둘 다 유지한다. ID 조회 후보가 99개인 로컬 측정에서 시간 차이는 작아, 이 결과만으로 짧은 인덱스가 꼭 필요하거나 삭제해도 된다고 확정하지 않는다. 등록·수정·삭제의 유지 비용과 더 큰 브랜드의 ID 정렬 비용을 비교한 뒤 최종 정리한다. 삭제의 트랜잭션·PK 잠금 순서는 변경하지 않았다. [확인 SQL](../../scripts/sql/week4-08-index-prefix.sql).
