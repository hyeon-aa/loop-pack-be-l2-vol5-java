## 조회 계약과 측정 환경

상품 10,000건에서 SQL 원리를 확인하고, 100,000건을 복사한 실험 DB에서 실제 앱을 비교한다. 원본 DB·개발 DB와 분리한 benchmark MySQL 8.0.46·InnoDB·REPEATABLE READ를 사용한다. 기존 상품 인덱스와 상품별 좋아요 카운터를 유지한다. 설정은 [setup.md](setup.md)를 따른다.

가격순은 `price ASC, createdAt DESC, id DESC`다. 브랜드 필터·삭제 상품/브랜드 제외·상품 표시 필드·현재 좋아요 수·page/size 검증을 지킨다. 좋아요순은 전체 후보의 좋아요 수로 정렬한 뒤 페이지를 선택한다. 빈 페이지는 빈 items로 반환하고 totalCount·hasNext는 제공하지 않는다.

총상품수 제외 결정의 이유와 응답 영향은 [ADR 0022](../adr/0022-product-list-without-total-count.md#이유와-결정)를 따른다.

## 실험을 읽는 방법

EXPLAIN으로 선택한 인덱스·예상 행 수·추가 정렬을 보고, EXPLAIN ANALYZE로 실제 단계별 반환 행·시간을 확인한다. 같은 연결에서 일반 SELECT 직전·직후 Handler 카운터 차이를 측정해 내부 읽기 요청을 보조 확인한다. Handler는 정렬의 CPU 작업, 디스크 읽기나 Root·Branch·Leaf 방문 횟수를 직접 보여주지 않는다.

결과 필드·순서를 먼저 확인하고, 읽는 범위·정렬·실제 행 조회와 시간을 함께 판단한다. 적게 읽었다는 사실만으로 API 전체가 빨라졌다고 결론 내리지 않는다. 직접 관찰한 결과와 구조에 대한 설명은 구분한다. 완료한 검증은 [implementation-log.md](implementation-log.md)에 기록한다.

### Handler 측정 도구의 자동 조회

현재 MySQL 확장은 일반 상품 SELECT 뒤 결과 전체 건수를 표시하려고 LIMIT 없는 COUNT를 자동으로 보냈다. 상품 페이지 20개 읽기 외에 COUNT의 99개 읽기가 합쳐질 수 있다. 실제 SQL 로그로 이를 확인했다. Handler로 페이지 SELECT만 평가할 때는 실행기의 같은 연결에서 구간을 통제한다. 현재 상품 목록 API에는 총상품수 COUNT가 없다. 확장의 표시용 자동 COUNT와 실제 API의 SQL을 구분한다.

## 상품 인덱스 실험

각 절의 인덱스 추가·삭제·유지는 해당 실험 시점의 기록이다. 현재 인덱스별 용도와 남은 판단은 [현재 조회 흐름과 인덱스](#current-query-flow)에서 함께 확인한다.

### 준비: 브랜드 7 조건으로 범위를 좁힌 조회

처음에는 전체 활성 상품을 가져와 Java에서 브랜드 7을 골랐다. 브랜드 조건을 SQL에 전달하면서 기존 `(brand_id, deleted_at)` 인덱스로 해당 구간을 찾게 됐다. 이 준비 단계에서는 정렬·LIMIT을 넣지 않았다.

```sql
SELECT p.*
FROM product p
WHERE p.brand_id = 7 AND p.deleted_at IS NULL;
```

전체 조회는 상품 10,000개를 훑고 9,699개를 반환했다. 브랜드 조건 조회는 99개를 읽고 반환했다. 인덱스를 새로 추가한 효과가 아니라 기존 인덱스로 필요한 범위를 찾도록 조건을 DB에 전달한 효과다. [실행 SQL](../../scripts/sql/week4-01-brand-filter.sql).

구조를 설명하면 Root·Branch를 거쳐 브랜드 7·미삭제 구간을 찾고 Leaf 항목을 따라 읽는다. SELECT p.\*에는 이름·가격처럼 기존 보조 인덱스에 없는 컬럼이 있으므로 기본키로 상품 행도 가져와야 한다. 이 그림은 구조 설명이며 실제 페이지 방문을 측정한 것은 아니다.

### 1. 가격순 정렬만 추가

상품 99개를 가격순으로 반환하기 위해 ORDER BY만 추가했다. 같은 가격의 순서도 일정하게 유지하려고 생성 시각·ID 내림차순을 포함한다.

```sql
SELECT p.*
FROM product p
WHERE p.brand_id = 7 AND p.deleted_at IS NULL
ORDER BY p.price ASC, p.created_at DESC, p.id DESC;
```

기존 브랜드 인덱스에는 가격 순서가 없으므로 해당 상품 99개를 읽은 뒤 별도로 정렬한다. SQL 반환도 99개다. **이 변경은 결과 순서를 맞추며 읽는 상품 수를 줄이지 않는다.** LIMIT·새 인덱스·좋아요는 이번 단계에 추가하지 않았다. [실행 SQL](../../scripts/sql/week4-02-price-sort.sql).

현재 읽기 흐름은 다음과 같다.

```text
브랜드 인덱스의 해당 구간 찾기
→ 상품 99개 읽기
→ 가격·생성 시각·ID 순서로 정렬
→ 상품 99개 반환
```

### 2. 가격순 20개 쿼리를 고정한 기존 인덱스 기준선

같은 쿼리를 고정하고 인덱스에 따른 탐색을 비교한다. 앞의 SQL 변경 단계는 준비 과정이다. 상품의 삭제 조건·동점 정렬을 유지하고 필요한 컬럼을 명시했다. 조회 컬럼을 바꾼 비교와 인덱스를 바꾼 비교는 구분한다.

```sql
SELECT id, brand_id, name, price, created_at
FROM product
WHERE brand_id = 7 AND deleted_at IS NULL
ORDER BY price ASC, created_at DESC, id DESC
LIMIT 20;
```

기존 `(brand_id, deleted_at)` 보조 인덱스의 같은 값 구간에서는 기본키 ID가 순서를 정한다. ID 순서로 조회한 예시는 `(id, price)`가 `(7, 26000) → (107, 96000) → (207, 66000) → (307, 36000) → (407, 6000)`이었다. 가격순이 아니므로 처음 발견한 20개를 바로 반환할 수 없다.

```text
기존 브랜드 인덱스에서 (7, NULL) 구간 시작점 찾기
→ 해당 구간 항목을 따라 읽기
→ 기본키로 이름·가격·생성 시각을 가져오기
→ 후보 99개에서 가격순 상위 20개 선택
→ 20개 반환
```

직접 확인한 계획은 Index lookup 99행 → Sort → Limit 20행이었다. Using index condition은 커버링을 뜻하지 않는다. 이름·가격·생성 시각은 기존 인덱스에 없으므로 일반적인 보조 인덱스 접근에서 실제 행 조회가 필요하다. Handler는 이 InnoDB 내부 기본키 조회를 별도 횟수로 보여주지 않는다. 트리 높이와 실제 페이지 방문은 이번에 측정하지 않았다.

[실행 SQL](../../scripts/sql/week4-03-fixed-product-page.sql)에 인덱스 키 순서를 이해하는 보조 조회도 넣었다. 보조 조회에만 FORCE INDEX와 ORDER BY id를 사용하며 고정 측정 SQL에는 힌트가 없다. 물리 Leaf 페이지를 덤프한 것은 아니다. 새 인덱스는 아직 추가하지 않았으며, 다음에는 동일 쿼리에서 인덱스 후보를 검토한다.

### 3. 가격 정렬용 복합 인덱스

같은 기준 쿼리를 유지하고 `(brand_id, deleted_at, price ASC, created_at DESC, id DESC)` 인덱스를 추가했다. WHERE의 앞 두 값이 고정된 구간 안에서는 ORDER BY의 세 컬럼 순서가 맞는다. 가격을 WHERE로 지정하지 않아도 해당 구간 시작점부터 가격순으로 읽을 수 있다. 결과 순서는 SQL의 ORDER BY가 보장한다.

#### 쿼리 패턴과 인덱스 컬럼의 대응

선정의 출발점은 **브랜드 조건이 있는 가격순 첫 20개 조회**다. 실제 서비스에서 가장 자주 호출되는 쿼리라고 측정한 것은 아니며, 이번 주차에 최적화 대상으로 정한 조회 패턴에 맞춰 설계하고 검증했다. WHERE·ORDER BY·LIMIT을 함께 보고 다음 역할을 컬럼 순서에 반영했다.

| 쿼리 패턴 | 인덱스에 반영한 이유 |
| --- | --- |
| `brand_id = ?` | 해당 브랜드 구간부터 찾는다. |
| `deleted_at IS NULL` | 같은 브랜드 안에서 미삭제 상품 구간으로 좁힌다. |
| `ORDER BY price ASC` | 앞 두 값이 고정된 구간을 가격 오름차순으로 읽는다. |
| `created_at DESC, id DESC` | 같은 가격에서도 API가 요구하는 생성 시각·ID의 동점 순서를 맞춘다. |
| `LIMIT 20` | 앞의 조건과 정렬을 인덱스로 처리해 첫 20개를 채우면 멈춘다. |

실제 API는 활성 브랜드 검사도 수행한다. 위 표는 상품 인덱스에 대응하는 조건·정렬을 설명하며, API의 모든 SQL을 이 인덱스 하나로 처리한다는 뜻은 아니다. [실제 조회 쿼리](../../apps/commerce-api/src/main/java/com/loopers/infrastructure/product/ProductJpaRepository.java).

카디널리티는 서로 다른 값의 수이며 컬럼 순서를 결정하는 단독 기준으로 삼지 않는다. 예를 들어 미삭제 상품이 많아 `deleted_at IS NULL`만으로 줄일 수 있는 행이 적더라도, 이번 쿼리에서는 브랜드와 삭제 상태를 고정한 뒤 가격순으로 읽는 역할이 있다. 고유값이 많은 컬럼을 무조건 앞에 두기보다 쿼리의 조건·정렬과 실제 읽기량을 함께 본다.

다만 이 쿼리에서는 `brand_id`와 `deleted_at`이 모두 고정되므로, 이 실험만으로 두 컬럼의 선후관계가 유일한 최적이라고 증명하지는 않았다. 브랜드를 선두에 둔 구성은 브랜드별 상품 조회·삭제 대상 조회 등 다른 패턴과도 맞으며, 기존 브랜드 인덱스와의 대체 가능성은 6절에서 별도로 비교했다. 모든 컬럼 순열을 비교한 것은 아니다.

이 사례는 **값을 고정하는 조건을 앞에 두고 그 구간 안의 정렬을 뒤에 맞춘 선택**이다. 모든 WHERE 컬럼을 정렬 컬럼보다 앞에 두는 공식으로 일반화하지 않는다. 범위 조건이나 여러 값을 합치는 IN 조건이 끼면 뒤 컬럼의 탐색·정렬 활용이 달라질 수 있으며, IN의 실제 결과는 8절에 기록했다. [MySQL 복합 인덱스](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html), [ORDER BY 최적화](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html).

```text
가격 인덱스의 (7, NULL) 구간 시작점 찾기
→ 가격 ASC·생성 시각 DESC·ID DESC 순서로 항목 읽기
→ 항목의 ID로 실제 행에서 이름 가져오기
→ 20개를 채우면 종료
```

기존 인덱스의 99행 접근과 Sort가 새 인덱스에서 20행 접근·Sort 없음으로 바뀌었다. Handler는 key 1·next 99에서 key 1·next 19로 바뀌었다. 첫 항목과 이후 19개를 얻는 읽기 흐름과 맞는 결과다. 이름은 인덱스에 없으므로 아직 커버링 조회가 아니다.

기존 브랜드 인덱스는 비교를 위해 유지했다. 선두 열 중복에 따른 저장·쓰기 비용은 정리 여부를 판단할 때 검토한다. 상품 가격·생성 시각·이름 등의 쓰기 비용은 이번 단계에서 측정하지 않았다. 이번 결과는 브랜드 조건이 있는 고정 SQL의 탐색이며 전체 API·브랜드 없는 조회의 개선을 보장하지 않는다. [실행 SQL](../../scripts/sql/week4-05-price-index.sql).

#### 가격까지만 포함한 후보와 전체 정렬 비교

ORDER BY의 모든 열을 인덱스에 반드시 넣어야 하는 것은 아니다. 인덱스는 별도 정렬 없이 같은 순서를 만들려는 선택이다. 같은 쿼리에서 `(brand_id, deleted_at, price)` 후보도 비교했다. 가격까지만 있는 후보는 같은 가격 안에서 생성 시각 DESC·ID DESC가 맞지 않아 이번 계획에서 99개를 읽고 Sort를 수행했다. 전체 정렬 후보는 20개만 읽고 Sort가 없었다. 두 후보의 결과는 같았다.

짧은 인덱스는 약 320KiB, 전체 정렬 인덱스는 약 400KiB로 관찰됐다. 이는 InnoDB 인덱스 페이지 할당 통계이며 정확한 유효 데이터 크기는 아니다. 동점 정렬을 포함하면 인덱스가 커지는 비용 대신 이번 쿼리의 읽기·정렬을 줄였다. 쓰기 시간은 별도 측정하지 않았다. 전체 정렬 인덱스를 유지하고 짧은 후보는 실험 후 삭제했다. 조건·데이터·정렬이 바뀌면 다시 판단한다.

#### 가격까지만 있는 후보의 자동 선택 재검토 기록

사용자가 전체 정렬 인덱스를 삭제하고 `(brand_id, deleted_at, price)` 후보만 추가한 상태에서 다시 확인했다. 힌트 없는 SQL은 기존 브랜드 인덱스를 선택했다. 가격 후보를 FORCE INDEX로 사용해도 같은 99개를 읽고 Sort를 수행했다. 두 경로 모두 WHERE의 같은 99개를 찾고, 같은 가격 안의 생성 시각·ID 내림차순을 별도로 해결해야 했다.

optimizer trace에서는 두 ref 후보의 예상 rows가 99, cost가 34.65로 같았고 기존 인덱스가 선택됐다. 범위 후보 평가도 두 cost가 34.91로 같았으며 가격 후보는 chosen=false·cause=cost였다. 표시된 정밀도로는 새 후보의 비용 우위가 없었다는 것까지 확인하며, 동률에서 기존 인덱스를 고른 정확한 내부 tie-break까지 증명했다고 보지 않는다.

현재 고정 쿼리에서는 가격까지만 있는 후보가 읽기·정렬을 줄이지 않아 별도 유지할 근거가 약하다. 하지만 가격만 정렬하거나 가격 범위를 거르는 다른 쿼리에서는 도움이 될 수 있다. 모든 쿼리에서 불필요한 인덱스라고 일반화하지 않는다. 사용자 직접 실험 중인 짧은 후보는 이번 확인에서 삭제하지 않았다.

옵티마이저는 후보를 모두 실행해 시간을 비교하는 것이 아니라 실행 전에 통계·인덱스 구조·조건·정렬·필요 컬럼을 바탕으로 비용을 추정한다. cost는 실제 밀리초가 아니다. 새 인덱스가 생겼다고 자동으로 채택하지 않으며, 기존 인덱스가 항상 우선한다는 규칙으로 해석하지 않는다. 예상의 정확성은 ANALYZE·Handler·실제 시간으로 확인한다.

### 4. 기본키 자동 포함과 정렬 방향은 다르다

05 인덱스에서 id DESC만 뺀 `(brand_id, deleted_at, price ASC, created_at DESC)` 후보를 비교했다. InnoDB 보조 인덱스는 기본키 ID를 자동 포함하므로 상품 행을 찾거나 ID 값을 얻는 데는 별도 id 선언이 필요하지 않다. 하지만 자동 포함 기본키 순서와 쿼리의 id DESC 요구는 구분한다.

같은 가격·생성 시각의 보조 조회에서 ID 1407 → 4407 → 7407이 나타났고, 그 ASC 순서 쿼리는 Using index·filesort 없음이었다. 원래 쿼리는 7407 → 4407 → 1407의 DESC 순서를 요구한다. 후보는 99개를 읽고 Sort로 원래 결과를 만들었고 05는 20개를 읽고 Sort 없이 같은 결과를 만들었다.

id DESC는 정확한 결과를 얻기 위해 반드시 넣는 열이 아니라, 이번 ORDER BY 전체를 인덱스로 처리하려고 방향을 명시한 것이다. 가격 ASC·생성 시각 DESC를 유지하면서 ID만 반대로 정렬하는 요구이므로 전체 인덱스를 역방향으로 읽는 것만으로 해결하지 않는다. 크기는 두 후보 모두 통계상 400KiB였으며, 기본키가 자동 포함되기 때문에 id를 명시했다고 별도 ID가 중복 추가됐다고 해석하지 않는다. [확인 SQL](../../scripts/sql/week4-06-implicit-id.sql). 비교용 후보는 삭제하고 05를 유지했다.

### 5. 커버링: 이름 제외와 이름 인덱스 추가

05 인덱스에는 브랜드·삭제 상태·가격·생성 시각·ID가 있지만 이름은 없다. 이름을 포함한 조회는 실제 상품 행에서 이름을 가져와야 한다. SELECT에서 이름만 제외한 원리 실험에서는 Using index·Covering index lookup이 나타났다. 두 조회 모두 상품 20개·Sort 없음·Handler key 1·next 19였다. 내부 기본키 조회는 Handler에 별도로 표시되지 않으므로 카운터가 같아도 커버링 여부는 다르다.

실제 API에는 이름이 필요하므로 이름 제거를 적용안으로 삼지 않는다. 사용자 제안으로 `(brand_id, deleted_at, price ASC, created_at DESC, id DESC, name)`도 비교했다. 정렬 기준 뒤에 이름을 넣어 원래 순서를 유지했고 이름을 포함한 원래 쿼리도 커버링 계획으로 바뀌었다. 같은 20개와 모든 필드를 반환했다.

이름 후보의 인덱스 할당량은 약 1,552KiB로 05의 400KiB보다 컸다. 이름 변경과 등록·삭제 때 추가 유지 비용도 고려해야 한다. 서버 SQL 중앙값 차이는 작았고 상품 20개만 가져오는 상황에서 실제 API·쓰기까지의 이득은 아직 확인하지 않았다. 이름 후보는 비교 후 삭제하고 05를 유지한다. 커버링이라는 이유만으로 즉시 채택하지 않는다. [확인 SQL](../../scripts/sql/week4-07-covering.sql).

Covering 계획은 필요한 값이 인덱스에 있어 일반적인 컬럼 확보 목적의 재조회를 줄인다는 근거다. MVCC 가시성 확인 등 모든 내부 상황에서 기본키 접근이 반드시 0임을 물리적으로 측정한 결과는 아니다.

#### 기억할 커버링의 의미

커버링은 인덱스 안에서 찾는 과정 자체를 없애는 것이 아니다. 쿼리에 필요한 값이 보조 인덱스에 모두 있어서 다른 컬럼을 얻기 위해 기본키로 실제 행을 다시 찾는 과정을 줄이는 것이다. SELECT뿐 아니라 WHERE·ORDER BY에 필요한 컬럼도 함께 본다. 같은 인덱스도 이름을 포함하는 쿼리와 제외하는 쿼리에서 커버링 여부가 다를 수 있다.

### 6. 기존 브랜드 인덱스의 선두 컬럼 대체 검토

#### 비교 전 확인할 점: 선두 컬럼 중복

idx_product_brand_price의 앞 두 컬럼은 idx_product_brand_deleted와 같은 `(brand_id, deleted_at)`이다. 복합 인덱스의 왼쪽 연속 컬럼으로도 탐색할 수 있으므로 브랜드·삭제 조건만으로 조회하는 경우 긴 인덱스의 앞부분을 사용할 수 있다. 물리적으로 인덱스를 잘라 별도 생성하는 것은 아니다. [MySQL 복합 인덱스 문서](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html).

다만 같은 조건을 찾을 수 있다는 사실만으로 모든 경로에서 짧은 인덱스가 불필요하다고 확정하지 않는다. 짧은 인덱스가 더 작을 수 있고, `(brand_id, deleted_at)`의 같은 값 안에서는 자동 포함 기본키 ID 순서인 반면 긴 인덱스는 가격·생성 시각·ID 순서다. 브랜드 일괄 삭제의 활성 상품 ID 조회는 ORDER BY id이므로 긴 인덱스로 대체할 때 Sort가 생기는지도 확인해야 한다. 잠금은 이후 단건 PK 순서로 얻는 기존 경계를 유지한다.

삭제 여부는 브랜드 조건 조회·COUNT·브랜드 삭제 대상 ID 조회 등 실제 SQL을 긴 인덱스로 처리했을 때의 결과·읽기·정렬과 인덱스 유지 비용을 비교한 뒤 결정한다. 기존 인덱스는 삭제하지 않았다. 아래 읽기 경로 대체 비교는 완료했으며 쓰기·삭제 전체 성능 검증은 남아 있다.

#### 비교 결과와 유지 판단

기존 인덱스를 삭제하지 않고 실제 세 조회 형태를 각각 기존·긴 인덱스로 강제해 비교했다. 브랜드 상품 조회와 활성 상품 COUNT는 긴 인덱스의 앞 두 컬럼으로 같은 범위를 찾았다. 두 경로 모두 99개를 읽고 같은 결과를 반환했다.

브랜드 삭제 대상의 `SELECT id ... ORDER BY id`는 달랐다. 기존 인덱스의 같은 브랜드·삭제 상태 구간은 ID 순서라 추가 정렬이 없고, 긴 인덱스는 가격·생성 시각·ID 순서라 별도 Sort가 추가됐다. 같은 조건을 탐색하는 기능은 겹치지만 모든 정렬을 동일하게 처리하지는 않는다.

이번에는 둘 다 유지한다. ID 조회 후보가 99개인 로컬 측정에서 시간 차이는 작아, 이 결과만으로 짧은 인덱스가 꼭 필요하거나 삭제해도 된다고 확정하지 않는다. 등록·수정·삭제의 유지 비용과 더 큰 브랜드의 ID 정렬 비용을 비교한 뒤 최종 정리한다. 삭제의 트랜잭션·PK 잠금 순서는 변경하지 않았다. [확인 SQL](../../scripts/sql/week4-08-index-prefix.sql).

### 7. 가격을 브랜드보다 앞에 두면

같은 가격순 20개 SQL에서 `(price ASC, brand_id, deleted_at, created_at DESC, id DESC)` 후보를 비교했다. 05의 컬럼을 유지하고 가격 위치만 앞으로 바꿔 브랜드 조건 탐색과 정렬을 구분했다. 후보 분리에 FORCE INDEX를 사용했으며 자동 선택도 따로 확인했다.

같은 `brand_id=7`·가격순·LIMIT 20 요청을 비교했다. 기존 측정 원본에서 확인한 흐름은 다음과 같다.

| 사용한 인덱스 | 실제 읽은 행 → 추가 정렬 → 반환한 행 |
| --- | --- |
| 가격 우선 | **1,600행 읽음 → 추가 정렬 없음 → 20행 반환** |
| 브랜드 우선 05 | **20행 읽음 → 추가 정렬 없음 → 20행 반환** |

두 경우 모두 Sort가 없었다. 하지만 가격 우선은 다른 브랜드가 섞인 가격순 항목을 읽으며 조건에 맞는 상품을 골라서 읽기량이 많았다. 1,600은 전체 상품 수가 아니라 이번 조회에서 실제 읽은 행 수다. “추가 정렬 없음”만 보면 두 방법의 이 차이를 놓친다.

따라서 **몇 행을 읽었는지, 다시 정렬했는지, 몇 행을 반환했는지**를 함께 비교한다. 힌트 없는 SQL은 05를 선택했으며 가격 우선은 비교용으로 강제한 경로다. 이 숫자는 1만 건 seed의 관찰값이며 다른 분포의 읽기량을 보장하지 않는다. [측정 원본 · price-first-index.json](measurements/index-results.json), [확인 SQL](../../scripts/sql/week4-09-price-first.sql).

### 8. 조건과 페이지가 바뀌면

| 검증 항목   | 직접 실행 SQL                                                    | 확인한 질문                                |
| ----------- | ---------------------------------------------------------------- | ------------------------------------------ |
| ① 열 순서   | [09 가격 우선](../../scripts/sql/week4-09-price-first.sql)       | 정렬을 피하더라도 넓게 읽는가?             |
| ② IN 조건   | [10 브랜드 IN](../../scripts/sql/week4-10-brand-in.sql)          | 각 구간의 가격순이 합친 결과의 가격순인가? |
| ③ 삭제 조건 | [11 삭제 조건](../../scripts/sql/week4-11-deleted-condition.sql) | 인덱스 밖 삭제 조건 때문에 더 읽는가?      |
| ④ 페이지    | [12 OFFSET·커서](../../scripts/sql/week4-12-offset-cursor.sql)   | 앞부분을 건너뛰는 읽기를 줄이는가?         |

#### 두 브랜드를 합치는 IN 조건

조건을 `brand_id=7`에서 `brand_id IN (7,8)`로 바꾸어 비교했다.

| 조회 조건·인덱스 | 실제 읽은 행 → 추가 정렬 → 반환한 행 |
| --- | --- |
| 브랜드 7·05 자동 선택 | **20행 읽음 → 추가 정렬 없음 → 20행 반환** |
| 브랜드 7·8·기존 브랜드 인덱스 자동 선택 | **198행 읽음 → 추가 정렬 있음 → 20행 반환** |
| 브랜드 7·8·05 강제 선택 | **198행 읽음 → 추가 정렬 있음 → 20행 반환** |

05는 `(brand_id, deleted_at, price, created_at DESC, id DESC)` 순서다. 브랜드 7만 조회하면 그 브랜드 안에서 가격순으로 읽는다. 두 브랜드를 조회하면 브랜드별 가격순 묶음을 읽으므로, 두 묶음을 합친 전체 가격순을 얻기 위한 Sort가 이번 계획에 남았다.

확인한 것은 **이번 두 브랜드 조회에서 기존 인덱스와 05 모두 198행을 읽고 다시 정렬했다**는 사실이다. “기존 인덱스를 선택한 것만이 Sort의 원인”으로 설명하지 않으며, “IN이면 어떤 인덱스든 반드시 Sort한다”로 일반화하지 않는다. 가격 우선 인덱스의 IN 조회는 이 실험에서 측정하지 않았다.

단일 브랜드와 두 브랜드는 대상이 달라 각각의 seed 기대값과 비교했다. [측정 원본 · index-conditions.json](measurements/index-results.json), [확인 SQL](../../scripts/sql/week4-10-brand-in.sql).

#### 삭제 조건이 인덱스에 없으면

복제 테이블에서 `(brand_id, price, created_at DESC, id DESC)`와 05를 비교했다. 원래 분포에서는 둘 다 첫 20개가 활성이라 차이가 없었다. 복제 테이블의 저가 활성 상품 70개를 추가 논리 삭제한 뒤, 삭제 조건 미포함 후보는 실제 행의 삭제 여부를 확인하며 91개를 읽어 20개를 골랐다. 05는 `(7, NULL)` 구간으로 20개만 읽었다. 둘 다 정렬은 없었다. 실제 상품 데이터는 변경하지 않았다.

#### OFFSET과 커서

활성 상품이 99개인 브랜드 7에서 OFFSET 60과 같은 위치의 커서를 비교했다. OFFSET은 80개를 읽고 앞 60개를 버려 20개를 반환했다. 커서는 기존 정렬의 세 값을 조건으로 받아 다음 구간에서 20개를 읽었다. 반환 컬럼·순서는 같았고 둘 다 Sort가 없었다.

커서는 가격 ASC에 >, 생성 시각·ID DESC에 < 조건을 사용했다. OR 범위 탐색의 추가 키 접근이 관찰됐고 이번 작은 데이터에서는 읽기 감소에도 SQL 시간이 더 빠르지 않았다. 따라서 커서가 항상 빠르다고 판단하지 않는다. 이전 페이지 마지막 값을 이미 가지고 있다는 사용 전제를 따르며 준비용 OFFSET 조회는 측정 밖이다. 현재 API는 page·size로 페이지를 지정한다. 실제 깊은 페이지의 규모 효과는 더 큰 후보 집합에서 후속 확인할 수 있다.

위 조건·페이지 비교의 공통 판단은 인덱스 존재·Sort 유무만으로 비용을 판단하지 않고 조건·분포·읽는 범위를 함께 보는 것이다. 실험용 테이블·인덱스는 정리했고 05와 기존 브랜드 인덱스를 유지한다.

<a id="like-count-design"></a>

## 좋아요 카운터 비정규화

상품 페이지를 고르는 인덱스 비교에 이어, 선택한 상품에 붙이는 좋아요 수의 저장·갱신 방식을 정리한다. 도입 배경과 대안 비교는 [ADR 0020](../adr/0020-like-count-denormalized-counter.md#context)에 있다.

좋아요 원본 관계와 별도로 `product_like_count`에 상품별 개수를 저장한다. 상품 엔티티에 like_count를 넣지 않는다. 좋아요 관계 INSERT/DELETE가 실제 반영됐을 때만 같은 트랜잭션에서 카운터를 원자적으로 증감한다. 중복 등록·없는 취소·rollback·동시 변경·생성 시 초기화·backfill을 검증한다([ADR 0020](../adr/0020-like-count-denormalized-counter.md)).

같은 상품의 좋아요 쓰기는 카운터 한 행에서 경합할 수 있다. 상품 행의 재고·가격 쓰기와 분리했다는 사실을 쓰기 비용이 없다는 뜻으로 해석하지 않는다. 좋아요순 전체 정렬을 임의의 20개 안에서 정렬하는 방식으로 바꾸지 않는다.

<a id="price-page-cache"></a>

## 가격순 첫 페이지 캐시

### 캐시 범위

브랜드 필터·가격순·첫 페이지 20개만 캐시한다. 값은 상품 ID·이름·가격·생성 시각이다. 총상품수·좋아요·브랜드 표시·재고·개인별 정보는 저장하지 않는다. [기본 흐름](cache-basics.md), [ADR 0021](../adr/0021-price-page-cache-aside-with-after-commit-eviction.md)을 따른다.

### 조회와 변경 후 삭제

Redis GET → miss면 기존 DB 페이지 조회 → SET+TTL 300초다. 상품 생성·이름/가격 변경·삭제와 브랜드 삭제가 같은 트랜잭션 안에서 PricePageChanged를 발행하고 AFTER_COMMIT listener가 해당 브랜드 첫 페이지를 DEL한다. rollback에서는 DEL하지 않는다. 페이지 밖 상품도 가격 변경으로 들어올 수 있어 무효화 대상이다. 좋아요·재고·브랜드 이름 변경은 가격순 페이지를 바꾸지 않아 DEL하지 않는다.

### 실패와 최신성

hit도 현재 브랜드와 캐시 상품의 활성 ID를 DB에서 확인한다. 삭제 상품이 있으면 DB에서 페이지를 다시 만든다. Redis 오류는 DB로 우회하고 DB 오류는 감추지 않는다. 쓰기 트랜잭션 내부 조회는 미확정 데이터를 캐시에 게시하지 않도록 우회한다. 정상 변경 완료 뒤 순차 조회는 새 결과를 반환한다. DEL 실패·늦은 채움에서는 표시 가격/이름/순서가 일시적으로 오래될 수 있으며 TTL은 SET부터 센다. 주문 금액·재고·포인트 판단은 DB 원본을 따른다.

## 캐시 없음·로컬·Redis 비교

같은 PricePageReader에서 provider만 바꾼다. 로컬은 Caffeine의 불변 DTO·최대 1,000개 엔트리·저장 후 300초 만료다. Redis는 JSON·master 전용 연결·200ms 연결/명령 제한이다. local/benchmark의 기본은 Redis이고 prefix는 각각 `commerce:price-page:v3:local`, `commerce:price-page:v3:benchmark`다. local 프로필 이름은 로컬 캐시 provider를 뜻하지 않는다.

캐시 없음은 `enabled=false`로 읽기/저장과 after-commit DEL을 모두 끈다. DB-only 쓰기 앱과 캐시 사용 앱을 같은 DB에 혼합 배포하는 설정으로 사용하지 않는다. 로컬은 다른 앱의 캐시를 지우는 기능이 없어 여러 앱의 변경 반영에 한계가 있다. 공유 Redis도 동시 miss를 한 번의 DB 조회로 합치지는 않는다.

[다섯 경우의 API 비교](price-cache-comparison.md)와 [일반/상품 쏠림·빈/채운 캐시의 동시 조회](price-cache-skew.md)를 구분한다. GET/PUT 전체 시간과 실제 변경 뒤 응답 정합성도 구분한다. Redis GET·JSON 변환은 같은 설정의 별도 Java 프로그램으로 확인하는 보조 측정이며 API 전체 시간에서 빼거나 순수 네트워크 비용으로 해석하지 않는다.

## 가격순 캐시 결론

**브랜드 7의 가격순 첫 20개 조회에서는 캐시의 뚜렷한 지연 개선을 확인하지 못했다. 현재 근거로는 운영 적용 시 캐시 없는 DB 조회를 우선 검토한다.** 과제의 Redis 학습 구현과 비교 결과는 유지하며, 현재 코드의 기본 Redis 설정을 끈 것은 아니다.

인덱스로 상품 페이지 선택을 줄인 뒤 캐시 없음·로컬·Redis를 비교했고, 두 앱의 가격 변경 반영도 확인했다. 이 절에 선택 이유와 비용의 확인 범위를 모은다. 상세 표본·실행 방법은 연결된 측정 문서에서 확인한다.

### 가격순에서 캐시가 필요한가?

일반 상품 10만 건의 복제 DB에서 브랜드 7·price_asc·page=0·size=20·X-USER-ID=95를 고정했다. 각 경우는 워밍업 100회 뒤 200회 측정하고 앱 실행 순서를 바꾸어 세 번 반복했다. 아래는 세 반복의 중앙값 범위이며, miss까지 포함한 전체 결과는 [다섯 경우 비교](price-cache-comparison.md)에 둔다.

| 방식 | API 중앙값 범위(ms) | 대표 요청의 업무 SELECT |
| --- | ---: | ---: |
| 캐시 없음 | 10.028~10.273 | 5 |
| 로컬 hit | 10.021~10.695 | 5 |
| Redis hit | 10.823~12.494 | 5 |

이 조건에서는 로컬·Redis hit의 뚜렷한 지연 개선을 확인하지 못했다. 상품 페이지 선택은 이미 가격순 인덱스로 20개를 읽는 경로다. hit는 이 선택을 활성 ID 확인으로 대체하고, 브랜드·좋아요 카운터·사용자·내 좋아요 여부의 DB 조회는 남는다. 캐시가 줄일 수 있는 작업이 작은 구조라고 해석하되, 각 비용이 전체 시간 차이에 기여한 비중까지 분리해 측정한 것은 아니다.

좋아요 수와 개인별 isLiked는 현재 DB에서 합성한다. 개인별 표시를 추가했다고 공통 상품 페이지의 재사용을 포기할 필요는 없다. 좋아요만 캐시하더라도 현재의 브랜드·삭제 여부·사용자 확인은 남으므로 DB 호출이 모두 사라지는 것은 아니다.

### 캐시 없음·로컬·Redis 중 무엇을 선택할까?

| 선택 | 확인한 이점과 책임 | 이번 가격순의 판단 |
| --- | --- | --- |
| 캐시 없음 | 캐시 저장·무효화·서버 간 전파 책임이 없다. | 확인한 조건에서는 운영 적용 시 우선 검토할 선택이다. 실제 서비스의 요구 응답 시간을 충족하는지는 별도 판단한다. |
| 로컬 | 캐시 읽기에 Redis 왕복이 없다. 두 앱 실험에서는 다른 앱의 옛 가격이 남았다. | 현재 측정에서 뚜렷한 지연 이득이 없고 다중 앱 무효화도 미구현이다. 이를 추가하는 작업은 후속 검토로 남긴다. |
| Redis | 두 앱이 공유 키를 사용해 정상 변경 후 새 가격을 읽었다. DB 변경과 캐시 무효화를 연결하는 책임은 계속 남는다. | 공유의 이점은 확인했지만 가격순 지연 개선을 근거로 운영 채택할 단계는 아니다. |

현재 local/benchmark의 기본 Redis 설정은 과제 학습 구현으로 유지한다. 이 설정과 운영 채택 판단을 구분한다. 캐시를 쓴다는 이유로 정합성을 생략하지 않으며, `변경 commit → DEL → 다음 조회에서 재채움`과 [가격순 첫 페이지 캐시](#price-page-cache)의 실패·늦은 채움 정책을 유지한다. 추가 정합성 구조를 도입할지는 요구 최신성과 새 비용을 근거로 별도 결정한다.

### 비용은 어디까지 확인했나?

GET·관리자 PUT 전체 시간, 별도 Java 프로그램의 Redis GET·JSON 변환 시간은 측정했다. GET 구간에는 통신과 클라이언트·Redis 처리가 함께 포함되므로 순수 네트워크 시간으로 부르지 않는다. JVM RSS와 Redis 키 메모리도 기록했지만 전체 앱 메모리와 개별 키 메모리여서 캐시 증분 메모리의 동등한 비교는 아니다.

실제 운영 hit rate·가격/좋아요 변경 빈도·지속 부하에서의 DB 자원 절감·최대 처리량·캐시 증분 메모리·다중 앱 무효화의 개발/운영 비용·월 비용은 아직 측정하지 않았다. 이 값을 추정해 결론에 넣거나 모두 추가 측정해야 가격순 실험이 완료된다고 요구하지 않는다. 상품 쏠림·동시 조회 결과도 [해당 조건과 한계](price-cache-skew.md) 안에서 읽는다.

현재 근거로 가격순 캐시 비교를 마무리한다. 다른 정렬의 비용과 캐시 필요성은 해당 조회 경로에서 별도로 확인한다. 가격순 단계의 회귀·Checkstyle·ArchUnit과 성능 원본은 [해당 실행 기록](implementation-log.md#price-cache-without-count), 과제 완료 근거와 제출 잔여 작업은 [Checklist 대조](implementation-log.md#price-cache-close-checklist)에 둔다. 관련 API/캐시 테스트에는 총상품수 응답이 없고, 기존 정렬·좋아요·가격 변경·삭제·rollback·실제 Redis 장애·늦은 채움 정책이 유지되는지 포함한다.

## 인기순 캐시: 순위는 60초 재사용하고 숫자와 하트는 현재 값으로

인기순은 순위의 잠시 늦은 반영을 허용한다. 상품 ID 목록을 재사용하고 현재 상품 정보·좋아요 수·내 하트는 DB에서 합성한다. 캐시가 없거나 실패했을 때도 DB로 다시 계산할 수 있어야 한다. 60초는 실험 시작 정책이며 최적값을 측정한 결과가 아니다([ADR 0025](../adr/0025-popular-page-snapshot-with-ttl.md)).

### 기존 좋아요순과 인기순을 구분한다

| 요청 | 순위 의미 | 범위 |
| --- | --- | --- |
| `sort=likes_desc` | DB에서 읽은 현재 누적 좋아요 수 DESC·생성 시각 DESC·ID DESC | 기존 브랜드/페이지/크기 계약 유지, 순위 캐시 미사용 |
| `sort=popular` | 같은 기준으로 최근 계산해 저장한 순위 | 브랜드 필수·page=0·size=20, 다른 조건은 400 |

인기순은 일정 기간 받은 좋아요나 별도 인기 점수가 아니다. 첫 페이지로 범위를 제한해 서로 다른 시점의 다음 페이지와 섞지 않는다. 가격순 캐시와 기존 정렬의 의미는 유지한다. 상품 목록 응답은 items·page·size이며 총상품수는 구하지 않는다.

### ID만 저장해도 무엇을 줄이나?

```text
브랜드 확인 → Redis에서 정렬된 상품 ID 20개 확인
  miss: 브랜드 전체 후보·카운터 조회 → Java 정렬 → 첫 20개 ID 저장
  hit: 저장된 ID의 활성 상품 조회 → 저장된 순서 유지
→ 현재 상품 정보·좋아요 수·내 좋아요 여부를 DB에서 합쳐 응답
```

재사용하는 것은 전체 후보에서 상위 20개를 고른 결과다. 캐시 값에는 ID만 있고 이름·가격·브랜드 표시·카운터·isLiked는 없다. 상품 캐시를 별도로 추가하지 않는다. 현재 숫자를 합치므로 A 100개·B 99개로 만든 순위에서 B가 101개가 되어도, 갱신 전까지 A가 위에 있을 수 있다. 숫자와 하트는 현재 DB 값이다. 공유 값에 개인별 상태를 넣지 않는다.

엄밀한 원천은 DB의 product_like 관계다. product_like_count는 같은 DB 트랜잭션에서 유지하는 파생 카운터이며, Redis 순위는 이 카운터로 다시 계산할 수 있는 사본이다. 순위 재생성마다 관계를 전부 COUNT하지 않는다. 카운터 검증·복구와 순위 재생성은 별개의 작업이다.

### 언제 유지하고 언제 다시 만드나?

| 상황 | 인기순 ID 캐시 | 응답의 표시 정보 |
| --- | --- | --- |
| 좋아요 등록·취소·중복 요청 | 유지, TTL도 연장하지 않음 | DB의 현재 숫자·사용자별 하트 |
| 상품 이름·가격·재고, 브랜드 표시 변경 | 유지 | DB의 현재 상품·브랜드 |
| 상품 생성·삭제, 브랜드 삭제 | commit 후 해당 브랜드 키 DEL | 삭제 대상은 DB 확인으로 비노출 |
| rollback | 기존 캐시 유지 | 미확정 데이터를 캐시에 저장하지 않음 |
| 만료 | 다음 조회에서 순위 재계산 | 현재 DB로 구성 |

키는 `prefix:brand:{brandId}:sort:popular:page:0:size:20`, TTL은 저장부터 60초다. hit로 만료를 연장하지 않는다. 정확히 매분 실행하는 배치가 아니며 요청이 없으면 재계산하지 않는다. 진행 중인 이전 조회가 늦게 저장될 수 있어 DB 변경 후 모든 요청에 적용되는 60초 절대 상한을 주장하지 않는다.

Redis가 실패하면 DB 원본 조회로 우회하고 DB 오류는 감추지 않는다. 삭제·다른 사용자 정보 비노출과 쓰기 트랜잭션 중 캐시 우회는 유지한다. 삭제/다른 브랜드 ID가 캐시에 남아 있어도 현재 DB 검증 뒤 다시 고른다. Redis 연결/명령 제한 200ms·master 전용 연결은 기존 가격순 캐시와 공유한다.

현재 local/benchmark는 `commerce.cache.popular.enabled=true`, `ttl-seconds=60`이다. prefix는 각각 `commerce:popular-page:v1:local`, `commerce:popular-page:v1:benchmark`다. false는 캐시 읽기/저장과 상품·브랜드 변경 후 DEL을 함께 끄므로 같은 DB에서 사용/비사용 쓰기 앱을 혼합 배포하는 설정으로 쓰지 않는다. 직접 SQL 변경은 앱 무효화를 거치지 않는다.

### 같은 10만 건에서 확인한 결과

기존 인덱스·복제한 상품 10만 건·브랜드 7·사용자 95·첫 20개를 고정했다. 각 경우는 워밍업 100회 뒤 측정 200회, 세 번 반복했다. 아래 시간은 각 반복 중앙값의 최솟값~최댓값이다. 변경이 없는 비교의 응답은 세 경우 모두 같다.

| 경우 | API 중앙값(ms) | 상품 / 카운터 행 | 업무 SELECT |
| --- | ---: | ---: | ---: |
| 캐시 없음 | 15.139~17.222 | 990 / 990 | 5 |
| Redis miss | 16.073~17.810 | 990 / 990 | 5 |
| Redis hit | 9.237~11.513 | 20 / 20 | 5 |

상품/카운터 행은 별도 대표 SQL 실행 계획의 접근 노드 actual rows이며 디스크 I/O 횟수가 아니다. SQL 수가 같아도 hit는 전체 후보 990개를 읽고 정렬하는 대신 상품/카운터 각각 20개를 읽는다. Redis 값은 ID만 담은 128바이트였다.

| 조건 | 캐시 없음 GET 중앙값(ms) | Redis GET 중앙값(ms) |
| --- | ---: | ---: |
| 변경 1회 / GET 10회 | 14.031~15.868 | 8.289~11.488 |
| 매 GET 전 변경 | 12.792~14.620 | 7.091~8.633 |

변경은 실제 좋아요 POST/DELETE이며 GET 시간에 변경 API 시간은 포함하지 않는다. 변경 중 캐시 없는 경로는 현재 순위, Redis는 저장된 순서와 현재 숫자·하트라는 각각의 기대값으로 검증했다. 서로 다른 순위 정책의 비용 비교이며 동일한 최신성으로 더 빨라졌다는 뜻이 아니다. Redis 혼합 실험에서는 각 GET 뒤 ID 값 유지와 TTL 감소를 확인했다. 운영 hit rate를 측정한 것은 아니다.

실제 기본 TTL도 한 번 기다려 확인했다. 좋아요 변경 뒤 이전 ID가 유지되고 기존 likes_desc는 새 순위를 반환했으며, 키 만료를 관찰한 뒤 첫 popular 조회에서 페이지 밖 상품이 진입했다. 측정 GET 6,000개와 측정 변경 API 1,320개의 상태·기대값을 확인했다. 원본 데이터·인덱스는 유지했고 전용 DB·키·앱은 정리했다([비교·검사 원본](measurements/100k-popular-cache.json)).

이 실험에서는 좋아요가 계속 바뀌어도 순위를 재사용하는 조건에서 이점이 있었다. 빈 캐시의 비용은 남는다. 지속 부하의 DB CPU·연결 대기·최대 처리량·운영 변경 빈도나 최적 TTL은 아직 측정하지 않았다.

### 이전 방식에서 바꾼 이유와 검증 범위

첫 구현은 likes_desc에 캐시를 붙이고 실제 좋아요마다 commit 후 DEL했다. 당시 매 조회 전 변경 조건에서 재사용 이점이 사라진 결과는 [이전 실험 기록](implementation-log.md#likes-cache-basic)과 [원본](measurements/100k-likes-cache.json)에 보존한다. 그 수치를 현재 인기순 구현의 재측정으로 취급하지 않는다. 기존 좋아요순의 정상 변경 후 반영 계약은 DB 경로로 유지하고, 지연을 허용한 인기순을 별도로 추가했다.

현재 전체 331건·Checkstyle·ArchUnit이 통과했다. 인기순 Redis 통합 17건에서 등록/취소 중 ID 유지와 숫자/하트 반영, 페이지 밖 상품의 만료 후 진입, 기존 likes_desc의 즉시 반영, 생성/삭제·rollback, 사용자 경계·잘못된 조건, 손상 값·DB 오류·늦은 채움·DEL 실패·전용 Redis 중단/재시작을 확인했다. 테스트의 짧은 만료와 실제 60초 관찰은 실행 기록에서 구분한다.

현재 정책의 측정·정확성 확인은 [구현 기록](implementation-log.md#popular-cache-snapshot)에 모은다. 한 앱의 Redis 캐시이며 Sorted Set·로컬 캐시 추가·주기 배치·분산 잠금은 도입하지 않았다. [가격순 캐시 결론](#price-cache-choice)은 유지한다.
